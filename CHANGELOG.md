## [1.13.1] - 2026-11-08

Security release from an audit of everything added since 1.12.3. The audit found no critical or high issues; this release fixes all its medium and low findings. The install gate was also verified live on FortiManager 8.0.2: a preview with changes authorizes exactly one install, and editing an object the package uses makes the preview stale.

**Upgrade notes:**
- `install_device_settings` now needs a verified `preview_install(package=None)` for the same ADOM and devices, like `install_package`. Set `FMG_INSTALL_SAFETY=warn` or `disabled` to keep the old behaviour.
- A preview authorizes only the exact device scope it covered: a scope entry without a `vdom` no longer matches a preview made for `root`. Install and preview scopes accept only `name` and `vdom` keys.
- `add_model_device` has a `confirm` parameter. Under `FMG_FIRMWARE_SAFETY=strict` (the default), a blueprint that enforces a firmware version (a firmware template or `prefer-img-ver`), or a saved blueprint that cannot be read, needs `confirm=True`. A name or serial number already in use is refused with `device_exists`.
- Meta-variable values containing `"`, `\`, `{{`, `{%`, `{#`, `$(`, C1 control characters or U+2028/U+2029 are refused.
- `query_device_api` refuses `filter`, `key`, `pattern` and `sort` on SNMP community tables, on secret fields, and whenever output masking is on. Below `monitor/switch-controller/managed-switch` only `status` is allowed.
- Install, script, add, clone and move requests are no longer retried after a dropped connection or a FortiManager internal error (-1).

### Security
- **Writes are no longer sent twice after a dropped connection.** Install, script run, add, clone and move requests are retried only when the connection could not be opened at all; a request that may have reached FortiManager is not replayed, so an install or script cannot run twice. Reads, set, update, delete and read-only exec calls keep the automatic retry; a stale session still reconnects once.
- **`install_device_settings` is gated like `install_package`.** Device-settings previews are recorded under their own target, and package and device-settings previews never authorize each other.
- **One preview authorizes exactly one install, also under parallel calls.** The preview record is taken before the first await, and installs to the same target run one at a time.
- **The preview gate keys on the exact scope.** Only `name` and `vdom` (stripped) form the key, and a missing vdom no longer counts as `root`. Verified live: before this fix, a vdom-less install passed a `root` preview.
- **A new preview cancels the previous one for the same target**, even if the new preview fails.
- **A preview is kept when its install was never sent** (no free task slot), and in `warn` mode an install that goes out spends the preview it used.
- **Device names with a VDOM suffix must be exactly `name[vdom]`.** Malformed bracket forms could pass the check and reach FortiManager URLs.
- **Validation patterns anchor at the very end and take ASCII digits only**, so a trailing newline or non-ASCII digits no longer pass name, address, port, firmware-version or schedule-time checks.
- **`query_device_api`:**
  - SNMP community strings are redacted in every community table, including switch-controller and wireless-controller child tables and bare entry lists.
  - Selector parameters can no longer be used to probe redacted or masked values, including through community child tables.
  - Only ASCII API paths are accepted.
  - The managed-switch monitor allowlist is narrowed to `status`.
- **Output masking (`FMG_MASKING`):** entry names and response keys that are addresses are masked in `query_device_api` output; addresses followed by punctuation in free text are masked; `username`, `user` and `user_name` (as user names) and `srcname` (as host name) are masked.
- **CLI template reads (`get_cli_template`) mask secrets in more Jinja forms**: assignments behind a secret `set` line, `pw`-style names, filtered block sets, dict literals and set lines after a comment.
- **Install preview and task output are redacted whatever envelope FortiManager returns**, and task-line details and history in install, preview, clone and `add_model_device` errors redact CLI-form secrets. `add_model_device` task details are also bounded in length and count.
- **`add_model_device`:**
  - It no longer suggests deleting a device that existed before the call. Partial creation is reported only when this call created the device.
  - It asks for confirmation before applying a blueprint that enforces a firmware version.
  - Password-type meta-variable values are masked in its result.
- **Meta-variable values refuse characters that could change how a template reads them.**
- **`clone_package` refuses an existing target name**, or a clone for which FortiManager returns no task, before writing anything.
- **Playbook prompt arguments are placed in a marked, size-capped data block**, so a value cannot pass for playbook steps.
- **The flow-trace HTML report template carries a Content-Security-Policy** that allows only its inline styles and no form or base URL, and a no-referrer policy.

### Changed
- The preview freshness check goes through one fingerprint function. It still compares the package revision, which was verified live on 8.0.2 to move when an object the package references changes.
- The install-status playbook says to use `find_object_usage` alone when output masking is on, since `query_device_api` then refuses `filter`.

## [1.13.0] - 2026-11-08

Feature release built on Laurent Venet's `lvenet` branch: 21 new tools (232 to 253) for SD-WAN, BGP, policy sync, CLI templates, policy blocks, metadata variables, firmware templates and a read-only FortiOS diagnostic proxy; eight troubleshooting playbooks served as MCP prompts; and fixes to install preview, `clone_package`, `wait_for_task` and `get_bgp_template`. Laurent's work was based on 1.12.0 and was merged onto 1.12.3 after a review; the review's fixes are listed with the entries they change and under **Security**. Live-verified on FortiManager 8.0.2 with FortiOS 7.4 and 7.6 devices.

**Upgrade notes:** `preview_install` now waits for the preview and returns the CLI itself (default 300 s) on FortiManager 7.6.7+/8.0.2+, and keeps the 1.12 task-based preview elsewhere. `list_tasks` returns the newest 100 tasks without per-device lines by default. `clone_package` creates an unassigned clone unless `copy_installation_targets=True`.

### Added

- **Eight troubleshooting playbooks, served as MCP prompts.** `src/fortimanager_mcp/skills/` holds eight `SKILL.md` playbooks that combine the tools for common jobs, and `prompts.py` serves each as an MCP prompt, so any MCP client can use them in both tool modes: `troubleshoot_sdwan_overlay`, `audit_firewall_policy`, `diagnose_install_status`, `diagnose_install_failure`, `check_template_rerun`, `trace_flow` (with the fortianalyzer MCP server), `locate_host` and `check_device_health`. Each takes one optional argument (`trace_flow` two). The prompt list is built from the files' frontmatter and read through `importlib.resources`, so it works from an installed wheel; the flow trace's HTML report template is served as the resource `fortimanager://skills/fmg-faz-flow-trace/references/report-template.html`. The playbooks read and propose: every change, install or device command waits for the user's approval, and every playbook tells the model to treat names, comments, task and log text and device data as data, never as instructions. `tests/test_prompts.py` checks every tool and argument a playbook names against the registered tools (and a checked-in list of the fortianalyzer tools), every FortiOS path against `query_device_api`'s allowlist, that every prompt renders and that the files are not gitignored. The review fixed a flow trace that called a FortiAnalyzer tool that does not exist (`search_log_file`; now `query_logs` with structured filters) and saved and opened its report with shell commands, and a device-health check that took `get_device_status` (FortiManager's database) for a live check. These are not fortianalyzer-mcp's `faz_skill` tool, which runs server-side orchestrations.
- **`set_metadata_variable` changes a device's metadata value.** A device can hold a mapping per scope (`global` and `root`), and a value changed in one scope can leave the other behind, so without `vdom` every mapping the device has is changed. The variable must exist, and the result lists old and new values, redacted for password variables. Mappings are addressed as `dynamic_mapping/{device}/{vdom}`.
- **`update_bgp_template` changes neighbor-group options in a BGP template.** It accepts `route-reflector-client`, `next-hop-self`, `next-hop-self-rr`, `soft-reconfiguration` and `advertisement-interval`, refuses anything else, and returns the values read back before and after.
- **`get_profile_group` reads a firewall security profile group.** Read-only, verified live on FMG 8.0.2.
- **`list_cli_templates` and `get_cli_template` read CLI templates.** `get_cli_template_group` lists a group's members only, so what a template pushes was out of reach. `get_cli_template` returns the script from `/pm/config/adom/{adom}/obj/cli/template/{name}` with secret directives redacted. Read-only.
- **`list_policy_blocks` and `list_policy_block_policies` read policy blocks.** A package shows a block as one entry with empty fields, and `list_firewall_policies` cannot open it. The policies are read from `/pm/config/adom/{adom}/pblock/{block}/firewall/policy`. Read-only.
- **`query_device_api` reads FortiOS diagnostic API paths through FortiManager.** It proxies a GET through `/sys/proxy/json`, so a device needs no direct route or credentials, and reaches live state (`monitor`) and running configuration (`cmdb`) that no dedicated tool covers. It sends GET only and reads only an allowlist of diagnostic path prefixes (system status and resources, HA peers, routing, sessions, policy hit counts, IPsec, ARP, FortiSwitch, cmdb firewall object tables and similar), matched case-insensitively; any other path, and any file export or dump even under an allowed prefix, is refused with the list. Query parameters are allowlisted too (so `plain-text-password` cannot be set). Secrets are redacted by field name and value (`ENC` blobs, PEM private keys, SNMP community names), device error messages are scrubbed and keep the device's HTTP status, and with `FMG_MASKING` on, addresses under unknown keys are masked by shape. The review replaced a block-list that refused only the exact segments `backup` and `download`. Read-only.
- **`get_device_bgp_status` reads live BGP state.** `get_device_bgp` shows the configuration only, so a peer stuck in `Connect` behind up tunnels and green SD-WAN health checks needed the FortiGate CLI. The tool proxies `router/bgp/neighbors`, `router/bgp/paths` and `router/ipv4` and returns peer state, paths learned from peers and the BGP routes in the routing table; a source it cannot read is listed under `unverified`. Read-only.
- **`get_package_install_status` and `check_device_policy_sync`: why is a package "out of sync"?** FortiManager flags a device's package as out of sync without saying what differs. The first tool returns the per-device status the GUI shows (`/pm/config/adom/{adom}/_package/status`). The second compares the package assigned to a device, policy by policy, with what the device has, from two sources: the latest device DB **revision** (what was last retrieved from or installed to the device) and the **device DB** itself (FortiManager's working copy, which also holds changes staged but not installed). With `source="both"` (the default) it also compares those two, so a change staged in FortiManager and not yet installed is told apart from drift on the device. Each comparison lists policies only on one side, modified fields, and whether the order matches. Policies are matched by UUID, install-on targets are resolved through nested device groups, policy blocks are expanded in place, and the package's normalized interfaces are translated to the device's own (per-device mapping, else the platform mapping for the device's model, else the default mapping, with `$(variable)` metadata resolved per device), so a mapped interface does not read as drift. Package and device DB tables are read with `verbose` so enums come back as the names FortiOS writes in its config, and a field FortiOS omits because it holds the default is read as that default. Live-verified on FMG 8.0.2 with FortiOS 7.4.12: the three installed devices compare clean, including branch3 where `port3` maps to `vl_lan` through a metadata variable, and the one out-of-sync device reports exactly the service change the install preview shows. Read-only.
- **Firmware templates: `list_firmware_templates`, `create_firmware_template`, `delete_firmware_template`.** Firmware templates (`/pm/fwmprof/adom/{adom}`) were readable only by name through the upgrade report. Listing decodes the enforced version per platform, the schedule, the image source and the assignment. Creating checks every version against the platform's firmware catalog (a bare `7.4.9` resolves to the catalog's `7.4.9-b2829`, an unknown version is refused with the nearby ones), refuses an existing name, writes the entries the way GUI-made templates store them, and leaves the template unassigned: assigning it is what makes FortiManager move devices to that version. Deleting is refused while the template is assigned. Live-verified on FMG 8.0.2.
- **`create_firewall_policy` and `update_firewall_policy` take `install_on`.** A policy's install-on targets (`scope member`), devices `{"name", "vdom"}` and device groups `{"name"}`, could only be set through raw API calls, so a rule meant for one branch in a shared package installed on every branch. Measured live on 8.0.2: an update replaces the list and an empty list clears it, which `update_firewall_policy(install_on=[])` now does.
- **`add_model_device` can apply a device blueprint.** New optional parameters: `device_blueprint`, `meta_variables` (the per-device values blueprint templates reference as `$(name)`, sent under the `meta variables` key the FMG GUI uses), and `groups`. `os_version` also accepts a patch level (`"7.4.12"` → `os_ver` 7.0, `mr` 4, `patch` 12, per the 8.0 dvmcmd schema). Meta-variable names are restricted to letters, digits, `_` and `-`, and values must be strings or numbers, so values with newlines or other control characters (and the redaction marker) are refused, because a template pastes the value into CLI as is and a newline would add CLI lines at the next install (review fix). The primary and HA member serials are validated and upper-cased, and blueprint object names are validated before they are looked up. Existing calls are unchanged.
- **`add_model_device` accepts an inline device blueprint.** `device_blueprint` may now be an object of `fmg/device/blueprint` attributes -- what the GUI sends when the blueprint option is unchecked -- as well as a saved blueprint name. Options accept `enable`/`disable`, booleans or 0/1; `auth-template`, `cert-template` and `prerun-cliprof` are sent as a single name, as the GUI does; an optional `flags` list (`create_task`, `nonblocking`, ...) is passed to `dvm/cmd/add/device` and the task ID returned; unknown attributes and `ha-password` are refused. Before adding, every object the blueprint names (policy package, template group, device groups, authorization/CLI/pre-run templates, provisioning templates, firmware template) is looked up, and so is a saved blueprint name: a missing object refuses the add (`blueprint_reference_missing`) instead of leaving a half-provisioned device; a lookup that fails for another reason is reported as `unverified_references` without blocking. When an add fails but FMG created the device anyway, the error says so (`partially_created`) instead of leaving the retry to fail with "Serial number already in use". A blueprint add runs as an FMG task (`create_task`, `nonblocking`) unless `flags` is given, and the tool waits for it: run inline, a failing blueprint step only returns -1 "Internal error", while the task history names the step and the reason (verified live on 8.0: `Pre-run CLI template [...] error: ... invalid ip`, `Authorization template [...] generation error: datasrc invalid`). Those come back as `task_errors`, with `partially_created` when the device record was written anyway.
- **`diagnose_ipsec_tunnel` diagnoses a down overlay tunnel, underlay first.** One read-only call gathers what an engineer checks before comparing IPsec proposals: the underlay interface the phase1 is bound to (admin status from the device DB, live link and address), the tunnel's live phase2 state (`monitor/vpn/ipsec`), its SD-WAN member and health-check state and, with `hub_device`, the hub's dial-up gateway matched on `network-id`, the hub underlay link and whether the hub holds an instance from this spoke. The verdict follows the first failing layer (`underlay_admin_down`, `underlay_link_down`, `underlay_no_address`, `hub_underlay_link_down`, `tunnel_down`, `health_check_down`, `sla_not_met`, `healthy`) with next steps, and lists any source it could not read under `unverified` instead of failing. Prompted by a live test on 8.0 where a branch's ISP2 NIC was disconnected: the tunnel's two phase1 configs were identical, and only the underlay link state explained the outage.
- **`install_device_settings` takes an optional `dev_rev_comments`.** The comment is passed to `/securityconsole/install/device` and labels the device revision the install creates, as the GUI install wizard does. It is trimmed, and an empty comment, control characters or newlines, or more than the 127 bytes FMG stores are refused before the install starts. Existing calls are unchanged.
- **`list_metadata_variables` and `check_device_variables`.** Read `/pm/config/adom/{adom}/obj/fmg/variable`: the first lists each variable's default and per-device mappings (or, for one device, the effective value and whether it comes from the device mapping or the ADOM default); the second compares a device against expected values, so a blueprint import can be verified variable by variable. Password-type variables are redacted.
- **`add_model_device` can declare a model HA cluster.** `ha_mode` (`AP`/`AA`), `ha_group_name`, `ha_priority` and `ha_members` send the add-model-only `ha_mode`, `ha_group_name` and `ha_slave` attributes of the 8.0 dvmcmd schema in the same `add/device` call; the member table lists the primary (role master) and each secondary (role slave). Duplicate serials or names, priorities outside 0–255 and a cluster without members are refused before any call.
- **SD-WAN template bodies, BGP and static routes are readable.** `get_sdwan_template` and `get_template` return only template metadata (`/pm/wanprof/...`, `/pm/template/...`), so an overlay built from an SD-WAN Overlay Template could be listed but not documented: its SLA thresholds, steering rules, BGP AS and neighbors were out of reach. Four read-only tools close that gap, with paths verified live on FortiManager 8.0.2 (the SD-WAN path is in the bundled 7.4 and 8.0 API references; the BGP template path in its 8.0.2 form is not, and the documented 7.x form is tried as a fallback): `get_sdwan_template_config` (`/pm/config/adom/{adom}/wanprof/{wanprof}/system/sdwan`), `get_bgp_template` (`/pm/config/adom/{adom}/template/router_bgp/{template}/router/bgp`), `get_device_bgp` (`/pm/config/device/{device}/vdom/{vdom}/router/bgp`) and `get_device_static_routes` (`.../router/static`). The BGP reads strip `neighbor.password` and `neighbor-group.password`, the two fields the schema marks `format=password`.

### Changed

- **`get_device_client_location` returns `fortiswitch_serial`.**
- **`get_device_bgp` takes `summary_only`.** The raw object lists some 150 fields per neighbor; with `summary_only=True` only the condensed summary comes back. Existing calls are unchanged.
- **`list_tasks` returns the newest tasks first, 100 by default, without their per-device lines.** The full history had reached 760,000 characters on a lab FMG. New parameters: `limit`, `since_hours` and `include_lines`, and the result carries `total`.
- **`diff_device_revision` compares configuration only and takes `sections`.** Blank lines and the `#` header are ignored, and `sections` limits the diff to named `config` blocks, since a revision also lists default objects the current export omits.
- **`list_firewall_policies` and `get_firewall_policy` return `scope member`,** the install-on targets of a policy.
- **`query_device_api` accepts `ip_version`, `summary`, `include_vlan`, `source` and `destination`.** `monitor/firewall/session` ignores `filter`, and in live tests also `port`, `policyid` and `srcintf`, so they are not forwarded.

### Fixed

- **Creating a TCP/UDP service with an admin that may not read the service table now logs in twice, not eight times (#118).** FortiManager answers a denied table with -11, the code a stale session gets too, so the client logs in again once and retries before it reports the denial. `create_service_tcp_udp` took that denial from each of its five named probes and from the list scan as a reason to try the next one, and then sent the create, so one call made seven requests that each logged in again for the same answer. Those logins succeed, so there was no lockout risk. `PermissionError` now stops the probing, as a failed connect or a failed login does since #107: a -11 that survives a fresh login means the service table itself is denied. The call still ends in `permission_denied`. Reproduced with a stub that answers every request with -11, not against an appliance.
- **`preview_install` reported `preview_failed` when there was nothing to install.** FortiManager ends that task in state 8 (`warning`) with "no installing devices/no changes on device", which the preview did not decode and polled until its deadline. All task states are now decoded, and the preview returns `has_changes: false` for each device. A warning with any other reason stays a failure.
- **`get_bgp_template` answered `permission_denied` for every template, even as a super user.** The path lacked the template's stype; it is `/pm/config/adom/{adom}/template/router_bgp/{template}/router/bgp`. A full read also leaves `route-reflector-client` out of the neighbor groups, so it is now read by name and merged in. Verified live on FMG 8.0.2.
- **`get_device_interfaces` left VLAN interfaces out.** It now asks for them with `include_vlan=true`.
- **`wait_for_task` waited until its timeout on tasks ending in `warning` or `aborted`.** Only states 0, 1, 3, 4 and 5 were decoded, so states 6-10 read as "unknown" and never ended the wait (verified live: an install with no changes ends in state 8 and was polled for the full 600 s). All 8.0 task states are now decoded; `warning` counts as completed with `status: success`, `aborted` as an error, and the result carries `task_state`.
- **`preview_install` previewed the last install task, not the package it was given.** It called `/securityconsole/install/preview` alone. Per the FNDN 8.0 spec that call renders a previously *staged* install (`preview_taskid`), and without one it falls back to "the last install task", so the result described whatever had last been installed. It now runs the complete Install Preview: stage with `install/package` (or `install/device` when `package=None`) and `flags=["preview"]`, render with that task's `preview_taskid`, fetch, and always cancel the staged copy. The preview comes back in the same call, per device, with a `has_changes` flag. A package that cannot be staged (e.g. a normalized interface with no per-device mapping) returns `preview_failed` with FortiManager's task lines, which name the cause. Live-verified on FMG 8.0.2. The review limited the staged flow to FortiManager 7.6.7+ and 8.0.2+: `preview_taskid` is in the 7.6.7 API reference only, and on a build that ignored it, the closing `cancel/install` could cancel another admin's install wizard in the ADOM. Other builds keep the 1.12 task-based preview, with a `warning`. The staged preview is now released on every path (success, error, nothing to install, a stuck stage, a cancelled call, a server stop within the shutdown budget); a failed release is reported as `warning` / `release_warning` with the call that frees the devices. Verified live on 8.0.2: a cancel naming another preview id left ours in place.
- **`install_package(preview=True)` left the target devices held by an install-wizard session.** It staged the package and never cancelled, so later installs and previews of those devices queued "Blocked by preview/install wizard" until the session was released. It now runs the same complete preview as `preview_install`.
- **Preview results were redacted before they were decoded.** On FMG 8.0 `preview/result` returns the per-device CLI as a JSON string inside `message`, so the CLI's newlines were still `\n` escapes when the line-based redactor ran over it and no `set <secret>` line could match. The envelope is now decoded first, in `get_preview_result` too, which also gains an optional `preview_taskid`.
- **`clone_package` always failed, and a working clone would have copied the device assignment.** It sent the new name as `new_name`, which FMG 8.0 rejects as an invalid parameter; `/securityconsole/package/clone` takes `dst_name`. Measured live on 8.0.2 once fixed: without `scope` the clone also copies the source's installation targets, so a package meant for review lands assigned to production devices; with `scope=[]` it is unassigned, but FMG clears every policy's install-on as well, so a rule meant for one device group would install on all. The tool now clones unassigned by default, copies each policy's install-on back from the source, waits for the clone task (returning its task lines if it fails), and runs under the shared task budget. `copy_installation_targets=True` keeps FMG's full copy.

- **`FMG_TOOL_MODE=dynamic` answered "Tool not found" for `list_policy_blocks` and `list_policy_block_policies`** (review fix): they were allowlisted under the wrong module. New catalog tests check, for every tool, that the dynamic allowlist names the module that defines it; `policy_sync` is its own category, and an exact category name in `find_fortimanager_tool` lists only that category. Verified through `execute_fortimanager_tool`.
- **`update_bgp_template` reported `route-reflector-client` as None before and after a change that took effect** (review fix): reading the group's own URL ignores `fields`. It reads the neighbor-group table with a name filter now, and a missing group is `not_found` before anything is written. Verified live on a throwaway template.
- **`diff_device_revision(sections="router bgp")` with a bare string matched nothing** (review fix): the string was split into characters. A single string is accepted now, and invalid values are refused.
- **The firmware template tools explain a refused template table** (review fix): FortiManager answers -6/-3 for a missing ADOM and for an API it does not have; the tools return `firmware_templates_unavailable` naming both causes. The template URL is not in the bundled API reference; create, list and delete are verified live on 8.0.2.
- **Nothing to install is not a failure.** "No installing devices" (package not assigned) and "no changes" are reported as nothing to install, and the strict install gate refuses the next install with that reason. The strict-mode refusal describes the current preview flow.
- **Install and preview scopes are validated:** `install_package`, `install_device_settings` and `get_preview_result` refuse an empty or malformed device scope, including an invalid `vdom`.

### Security

- **`get_device_sdwan` no longer returns health-check probe passwords.** The schema marks `system.sdwan.health-check.password` as `format=password` (the credential an HTTP or FTP probe authenticates with), and the tool returned the raw object unstripped. It now removes that field, as does the new `get_sdwan_template_config`, which reads the same schema from a template.
- **Meta-variable values cannot inject CLI** (review fix): `add_model_device(meta_variables=)`, `set_metadata_variable` and `check_device_variables` refuse newlines and other control characters. Unit tests and a live refusal on 8.0.2.
- **`get_cli_template` redacts Jinja-style secrets** (review fix): `{% set psk = ... %}` and block assignments with secret-looking names, secret-keyed literals inside tags, `set <secret>` lines after a tag, quoted multi-line values and `ENC` values. Bare `{{ var }}` and `$(var)` references stay visible. Checked live with a template full of fake secrets.
- **Task lines are redacted wherever they are returned** (review fix): `summarize_task_lines` runs the free-text redactor over each line's detail and history, which can quote the value a step failed on.
- **With `FMG_MASKING` on, the new BGP, IPsec, static-route and device-API tools mask addresses** (review fix): `neighbor_ip`, `local_ip`, `learned_from`, `next_hop`, `remote_gateway` and `rgwy` are address keys, and `prefix`, `prefix6`, `dst`, `router_id` and `remote_gw` are masked when the value is shaped like an address (they hold names or ids on other records). IPv6 interface prefix lists are masked too. `diagnose_ipsec_tunnel` keeps the peer address in `evidence` only, not in its free-text explanation. Live check: no address left after masking.
- **Names that go into FortiManager URLs are validated** (review fix): policy block names (`list_policy_block_policies`, `check_device_policy_sync`) refuse `/` and `..`.

## [1.12.3] - 2026-11-08

Patch release: fewer pointless FortiManager logins when it is unreachable or the login fails, results that match what FortiManager 8.0 actually returns, an empty `search_objects` term refused, and `mcp` held to 2.x.

### Fixed

- **Creating a TCP/UDP service when FortiManager is unreachable or the login fails now makes one connect attempt, not seven (#107).** `create_service_tcp_udp` discovers the ADOM's TCP/UDP protocol code before the create by fetching up to five predefined services by name, then scanning the service list. With `connect_on_demand` every request connects first, and each probe swallowed its failed connect and tried the next name, so one call made five probe connects, one for the scan and one for the create. Against an unreachable appliance each waited out `FORTIMANAGER_TIMEOUT`; with username/password auth and a wrong password each was a failed login, seven per call, past FortiManager's default `admin-lockout-threshold` of 3. The probe and the scan now raise on a `ConnectionError`, a network error (`OSError`, already retried inside the request) or an `AuthenticationError`; a not-found or any other per-object error still moves on to the next name, and nothing is cached on failure. Measured against 192.0.2.1 with `FORTIMANAGER_TIMEOUT=3`: the call fails after 3.0 s with one failed connect (was 21.0 s with seven), same error envelope. The failed-login case is pinned by a test (one login attempt, was seven) and was not reproduced against an appliance, since that would trip the lockout it is about.
- **`search_objects` refuses an empty `search_term` instead of returning the whole ADOM inventory (#108).** Since #98 the term goes out as `like "%<term>%"`, so an empty term became `like "%%"`, which matches every name, and one call returned every address, address group, service and service group in the ADOM in a single response. Before #98 the same call sent `contain ""`, which compares the field whole and so did not list everything. The tool is a search and the `list_*` tools already list; nothing in the repo relied on an empty term. It now returns `validation_error` and names the four `list_*` tools. A term of only spaces is still searched as written, since names do contain spaces.
- **An empty script-log response is no longer reported as a script execution (#115).** FortiManager answers the script-log endpoints with a success envelope and no `data` member when the ADOM has no script history, and pyfmg hands back the whole result object in that case. `get_script_log_summary` wrapped that object in a list and returned `count: 1` with `{"status": ..., "url": ...}` as the one execution, and `get_script_log_latest` returned the same object as the log. The summary is now empty with `count: 0` and the latest log is `null`. Measured on FortiManager 8.0.2 with no script history; 7.6.8 with history returned real records before and after.
- **`get_fmg_license` reports the contract count on FortiManager 8.0 too (#116).** The tool documents `license` as the contract list and its count. 7.6.8 answers `/um/license/self` with both; 8.0.2 sends the contract list without `count`, so the documented key was missing there and a caller reading it got a `KeyError`. When the appliance sends a contract list and no count, the tool now fills `count` in from the list. A count the appliance did send is passed through unchanged.

### Changed

- **`mcp` is held to the 2.x major: `mcp>=2.0.0,<3` (#109).** The floor had no ceiling since the 2.x port (#92), so a fresh install would resolve mcp 3.0 the day it ships. That is the failure #38 fixed for 2.0: an unbounded spec let a new major in, and the server stopped importing. The server depends on more than the public import path: the masking wrapper patches `mcp.tool`, and the 2.0 bump moved `stateless_http` and `transport_security` out of the constructor, where dropping them would have left the HTTP deployment unbound by `MCP_ALLOWED_HOSTS` with nothing reporting it. The ceiling matches fortianalyzer-mcp, which already declares `<3`, and moves when the server is ported to the next major. No installed version changes: the resolver still picks mcp 2.3.0. `tests/test_dependency_contract.py` pins the spec.
- **Dependabot keeps the SHA-pinned GitHub Actions current (#110).** Every action has been pinned to a full commit SHA with its release as a trailing comment since 1.9.0, which stops a moved tag from changing what CI runs but also stops the pins from moving at all: they still name the releases current when they were last bumped by hand. `.github/dependabot.yml` now updates them weekly, comment and SHA together, minor and patch releases as one grouped pull request and a major release on its own. One pin is corrected with it: `codecov/codecov-action` named the SHA of its annotated `v6` tag object rather than a commit, and now names the commit that tag points at (v6.0.2), the same code.
- **`get_ha_status` describes what FortiManager returns (#117).** The docstring promised the HA mode, the cluster members, the sync status and the role, with an example reading `result['data']['mode']`. On a standalone unit `/sys/ha/status` returns only `{"HA Health Status": "OK"}` (7.6.8 and 8.0.2), so the example raised `KeyError`. The docstring now says so and points to `get_system_status`'s `"HA Mode"`. The tool's behaviour is unchanged.

## [1.12.2] - 2026-11-06

Patch release. **Upgrade if the server runs under Docker, systemd or Kubernetes:** a stop could take from 30 s to over a minute, or never finish while an MCP client held a stream open, so the supervisor ended it with SIGKILL and the ADOM lock release and logout never ran. A stop now takes at most about 7 s, inside `docker stop`'s 10 s.

### Fixed

- **A stop no longer waits for the supervisor's SIGKILL while an MCP client holds a stream open (#113).** At shutdown uvicorn waits for every open connection before it runs the lifespan shutdown, with no limit unless `timeout_graceful_shutdown` is set, and an MCP client keeps a stream open: on the 2026-07-28 protocol a `subscriptions/listen` request is a standing notification stream, which mcp's handler ends only when the client disconnects. So a stop logged `Waiting for connections to close.` and then waited for the supervisor: under systemd every stop sat out `TimeoutStopSec` (90 s by default) and ended in SIGKILL, and `docker stop` gives up after 10 s. `run_http` now passes `timeout_graceful_shutdown`, first 5 s and lowered to 3 s by #114 so that the whole stop fits `docker stop`'s 10 s; after it uvicorn cancels what is left and the lifespan shutdown runs as usual. Each stream cancelled that way logs uvicorn's `Cancel N running task(s)` and an `Exception in ASGI application` traceback ending in `CancelledError`, which is expected on stop. uvicorn 0.30.0, the declared floor, has the parameter. Measured on two systemd units with five connected clients each: the stop took 90.2 s and ended in SIGKILL before, 5.2 to 5.4 s after with the 5 s bound.
- **Stopping the server no longer waits out `FORTIMANAGER_TIMEOUT` when FortiManager has stopped answering, and the whole stop fits `docker stop`'s 10 s (#114, twin of fortianalyzer-mcp#158 and #165).** Every stop releases ADOM locks still held through `lock_adom` and then disconnects, and each of those requests ran on the full request timeout, 30 s by default. With an API token the logout had nothing to end: pyFMG's token "session" is a UUID it makes up on the client, and every request carries the token. Each held lock added another wait, and it doubled: `release_held_locks` gives up on an unlock after 5 s, but `asyncio.wait_for` only stops the await, the pyFMG thread keeps running, and `_run_fmg_call` hands the request lock to it, so the next request queued behind that thread for the full timeout. `docker stop` sends SIGKILL after 10 s, so a container in that state was killed on every stop, and 30 s already runs into Kubernetes' default 30 s grace period. Token mode now skips the logout and only closes pyFMG's HTTP session. Before the unlocks, the server gives the client one 4 s budget for all its remaining FortiManager requests (`prepare_shutdown`): each request runs on pyFMG's own timeout lowered to what is left of it, which bounds the request itself and stays below the 5 s unlock wait, so no thread is left behind; a request after the budget is used up is not sent; and each is one attempt, with no retry or reconnect. Username/password mode still logs out, on a timeout capped at 3 s; if the unlocks used up the budget the logout is skipped, and FortiManager ends the session, and any lock it still holds, when the session times out. The wait for open connections from #113 is lowered from 5 s to 3 s, as in fortianalyzer-mcp, so the two add up to at most 7 s; a tool call still running 3 s after the stop starts is cancelled, and its client gets an error. Measured with `FORTIMANAGER_TIMEOUT=30` against a localhost HTTPS stub that answered the connect and then went silent: token mode exits 0.2 s after SIGTERM and 0.1 s after stdin closed (both were 30.2 s); username/password 3.2 s after either (was 30.2 s); with ADOMs locked 4.1 to 4.2 s, for one lock or two (was 60.2 to 60.3 s); and with a client holding a 2026-07-28 `subscriptions/listen` stream open, username/password and two ADOMs locked, 7.3 s (was 65.2 s with #113's 5 s wait). **Still open:** a stdio server whose startup connect is still running against an unreachable FortiManager stays up until that connect times out, because `asyncio.run()` waits for the worker thread when it exits (30.0 s and 30.4 s after stdin closed at the default timeout, measured against 192.0.2.1 in both auth modes).

### Changed

- **The setup guide's tool count and category table match the 232 registered tools (#112).** `docs/SETUP_GUIDE.md` still said 101 tools in 7 categories; it now says 232 in 17, with a row per module, checked against the tools the server registers in full mode (232, plus `health_check`).

### Tests

## [1.12.1] - 2026-11-03

### Fixed

- **A failed version probe no longer pins the legacy script endpoint (#106).** The script tools pick their endpoint from the FortiManager version, `/pm/config/adom/<adom>/obj/fmg/script` on 7.6 and later and `/dvmdb/adom/<adom>/script` before that, and the version is probed once and cached. A probe that failed for any reason cached the 7.0.0 fallback, so one script call made while the appliance was unreachable sent every later script call to the pre-7.6 endpoint, with the pre-7.6 string `target` values, until the server was restarted. Since #103 the server keeps running while FortiManager is down, so an appliance reboot during a script call is enough to trigger it. A probe that fails because FortiManager cannot be reached, either a failed on-demand connect or a transient error from a session that dropped, now raises: the real request would fail the same way, so the script call fails after one connect wait instead of two, and a script write never goes to a guessed endpoint. Measured against an unreachable host with `FORTIMANAGER_TIMEOUT=3`: 4.0 s per script call, against 8.0 s with the fallback applied to every call. Any other probe failure, such as a version string that fails to parse, takes the 7.0.0 fallback for that call only and is not cached, so the next script call probes again, the way FortiAnalyzer's timezone lookup already treats a probe that raised.
- **An unreachable FortiManager no longer stalls startup or leaves the tools dead (#103).** Both transports awaited the FortiManager connect before serving. With the appliance unreachable, a stdio server answered `initialize` only after the connect timed out, 31 s with the default `FORTIMANAGER_TIMEOUT` of 30, which is past Claude Code's own 30 s MCP connect timeout, so the server showed as failed; in HTTP mode `/health` did not answer for those 31 s either. The failed connect also dropped the client, so every tool answered "FortiManager client not initialized" until the process was restarted, even once the appliance was back. The server now serves at once and makes the startup connect in the background, and its client, when not connected, connects on its next request, so tools work as soon as FortiManager is reachable. Tool calls that arrive during one connect attempt wait for it and share its result instead of each waiting out another timeout. The connect-on-request is opt-in (`FortiManagerClient(connect_on_demand=True)`) and only the server sets it, so a client used directly still raises "Not connected" until `connect()` is called. Measured with an unreachable host: `initialize` in 1.0 s (was 31.1 s), `/health` in 1.2 s (was 31.2 s); a tool call then returns `connection_error` after the connect timeout.
- **The server reports its version in the MCP handshake (#101).** `MCPServer` defaults `version` to an empty string and the server never passed one, so every client received `serverInfo.version == ""` on `initialize` and could not tell which release it was connected to. The constructor now takes `fortimanager_mcp.__version__`, and a test drives a real `initialize` through the in-memory client and asserts the name and version the client sees. The parameter exists from mcp 2.0.0 on, so the dependency floor is unchanged.
- **A settings error now says when no `.env` was read, and which path was checked (#104, twin of fortianalyzer-mcp#143).** `utils/config.py` finds the `.env` by walking four parents up from itself, which is right for a `src/` checkout and an editable install and wrong for a regular `pip install .` or a wheel, where the walk lands one level above `site-packages`, at `lib/python3.X/.env`. The file was then dropped from the settings sources with nothing logged, and with `env_file=None` pydantic-settings reads no dotenv from anywhere, the working directory included. The first symptom was a validation error naming a field the user had set in the file, with nothing in it to search for. The error now carries a note with the absolute path that was checked, that a working-directory `.env` is not read either, and to set the variables in the environment. It rides the exception as a note rather than a log line because the server loads settings at import, before `logging.basicConfig` runs, so a log line at that point never reaches the console; a healthy start prints nothing new. The README states which installs read a `.env`.

## [1.12.0] - 2026-10-23

### Security

- **Config-text redaction covers every password-typed directive (#99).** `get_device_revision`, `diff_device_revision` and the policy install preview mask secrets in FortiOS CLI text by directive name, and that list held 31 of the 123 `format=password` names in the bundled cdb-device swagger for 7.0 through 8.0. A pre-release sweep caught the gap: the latest revision of a live 7.6 FortiGate came back with `old-password` (`system admin`, an `SH2` hash), `key-passwd` (`system sdn-connector`) and `fixed-key` (`system csf`) as `ENC` values, while the other 211 in the same export were masked. The last two are reversible under the fixed FortiOS key on a device without `private-data-encryption` (Fortinet FG-IR-19-007). The list now carries every password-typed name from the schema instead of growing one report at a time, and a fallback masks any `set <directive> ENC …` line whatever its name, so a field a future FortiOS adds is covered before the list knows it. Secrets that are not ENC-encoded still depend on the list. Over-redaction is limited to `sim1-pin`/`sim2-pin`, which are plain strings under `extender-controller`. Verified on two live devices: 214 and 25 `ENC` values in, none out, and against the previous redactor no line changes other than the four that leaked. The revision tools are new in this release, so the gap never shipped.
- **`get_device_interface_config` strips interface credentials (#97).** The tool returned the raw device-DB `system interface` objects with nothing removed, so every interface's stored `password` (PPPoE), `eap-password` (802.1X) and `pptp-password` reached the caller as `ENC` blobs. Those are not safe to hand out: unless `private-data-encryption` is enabled, FortiOS encrypts them with a fixed key that is public. The VAP, WTP, phase1 and SSL-portal reads already stripped their credentials, and this path had been missed since the tool was added in #43. The field set comes from the bundled cdb-device swagger for 7.0 through 8.0 rather than from the fields the report happened to show: every `format=password` field on the table, which adds `wifi-key`/`wifi-passphrase` at the top level plus `l2tp-client-settings.password` and three `wifi-networks` fields nested, covered by the same recursive strip `vpn_tools` uses. The leak is not limited to interfaces that use those features. A live 7.6.7 read of the 35 interfaces on a test FortiGate returned 71 `ENC` values on ordinary ports, and the tool output now contains none. The condensed `summary` key was never affected.
- **The model-device echo strips credentials too (#60, closes #53).** #51 covered the four read paths and the two `add_device` echoes, but `add_model_device` echoed the FortiManager-returned object unstripped, so the same stored admin password came back on a path the earlier fix had not enumerated. It now routes through the same shared helper as the rest, and the test asserts membership of the set of credential-returning tools rather than naming them one at a time, so a new device-creating tool cannot quietly reopen this.

### Added

- **Reversible data masking (FPE), ported from the FortiAnalyzer layer (#39, closes #34).** With `MASKING_ENABLED=true` and a key, IOC-bearing values (device and management IPs, subnets, IP ranges, serials, FQDNs, admin usernames) are replaced by reversible, deterministic tokens, so a model can still correlate a value across calls without holding the value. Tokens are also refused as inputs, at any depth and inside free text, before the tool body runs. Off by default, and enabling it without a valid key aborts startup rather than running unmasked. Object, ADOM and package names are deliberately never masked, because they route follow-up calls.
- **The ten highest-priority missing tool groups (#65).** Security-profile object CRUD (AV, web filter, DNS filter, application control, IPS sensor including signature overrides, SSL/SSH inspection, DLP, WAF), which closes the gap where firewall policies could reference a profile by name that nothing in this server could create; IPsec phase1/phase2-interface CRUD and SSL-VPN settings plus web portal; device-group create/delete, member add/remove and nesting; revision history (list, get, diff, revert) for device DB, ADOM DB and firewall-policy history; firmware upgrade path, catalog, trigger and report; an object-usage graph for where-used and duplicate detection; FortiManager appliance operations (backup/restore, packet capture, license, task cleanup); and local-in policy CRUD for management-plane access control in both address families.
- **`firewall.sniffer` and `firewall.on-demand-sniffer` device-DB tools (#77).** Two separate FortiOS cmdb tables that happen to share a word, confirmed against the 7.6.7 Configuration API spec: the first is ID-keyed and runs continuously while `status=enable`, the second is name-keyed and bounded by `max_packet_count`, which exists only on that table. Neither is FortiManager's own local diagnostic sniffer, which the existing appliance packet-capture tools still target. Both stage into the device DB only; nothing reaches the device until `install_device_settings`.
- **A 6 GHz radio is guarded against a VAP whose security mode cannot work there (#62, follow-up to #47).** The guard keys off the **band, not the radio index**, because the index does not determine the band: the schema offers the 6 GHz bands on every index, so an index-keyed guard would refuse a legal WPA2 SSID on an AP whose radio 3 happens to be 5 GHz. The refuse tier holds only what the review attested, that 6 GHz is WPA3-only and anything else is rejected at install time. It is deliberately narrower than first offered: writing the full table of what a 6 GHz radio accepts would mean writing down what could not be measured here, so the remainder warns rather than refuses.

### Fixed

- **"Partial match" filters matched only exact names, and combined filters were a union (#98, by Terji / [@keyboardCurry](https://github.com/keyboardCurry)).** Every `name_filter`, `search_term` and `platform_filter` was sent as `["name", "contain", term]`, which FortiManager 7.6.7 compares whole against a scalar string field, so `list_service_groups(name_filter="Veeam")` found nothing and `search_devices(name_filter="Office")` missed `Main_Office`. They now go out as `like` with `%` wildcards, with `%`, `_` and `\` in the term escaped (measured live, `_` is a single-character wildcard and a backslash escapes it), through one shared `substring_filter`. `os_version_filter` could never match at all, because dvmdb splits the version across the integer fields `os_ver`, `mr` and `patch` and neither operator matches an integer field, so "7.4" is now parsed into `os_ver == 7 && mr == 4` and a malformed value is refused. Separately, a bare list of filter conditions is an OR on the appliance (`name like %oob%` plus `type == fqdn` returned all 482 FQDN addresses), so every tool that combines narrowing parameters now joins them with `"&&"` through `and_filters`. `contain` stays on a policy's `srcaddr`/`dstaddr`/`service`, where it means list membership, and a test fails if it reappears on any other field.
- **`list_scripts` was the one combining site #98 did not reach, and the version validator accepted non-ASCII digits (#100, follow-up to #98).** `script_type` and `target` together went out as a bare condition list, which the appliance reads as an OR, so the two parameters widened the result instead of narrowing it. They now go through `and_filters` as well, and the FortiManager 7.6+ mapping of `target` to an integer still reaches inside the joined form. The lab holds a single script, so the union was not reproduced on this endpoint; the OR reading is the one #98 measured on the object and dvmdb tables and re-measured here on 7.6.7 build 3737. Separately, `_os_version_filters` checked each part with `str.isdigit()`, which is true for a superscript two (`int()` then raised, and the caller saw Python's own message instead of the validator's) and for Arabic-Indic digits (read as the Western ones, so they silently became 7.4). Each part must now be ASCII as well.
- **Two tools existed but dynamic mode could neither discover nor dispatch them (#61, closes #58).** `get_policy_services` and `update_service_group` were missing from the hand-written catalog and the per-module dispatch allowlist, which is how they survived several releases unreachable. The fix that matters is the test: it parses the `@mcp.tool()`-decorated functions out of the tool modules and both literals out of `server.py` and asserts they agree, so the class is closed rather than the two instances.
- **FortiAP-U and FortiAP-S serial prefixes are accepted (#63, closes #56 part 2).** The validator recognised only the base prefix, so two shipping hardware families were refused by name.
- **wtp-profile radio writes were rejected outright, and a wide 6 GHz channel was silently written wrong (#64).** The read-modify-write echo carried back read-only bookkeeping keys the API injects on GET, which made FortiManager reject the whole request on **every** radio rather than in a specific case. Separately, FortiOS stores a wide 6 GHz channel as the full list of its member 20 MHz sub-channels, while the device-DB write accepts a single-element list without complaint, so pinning a wide channel by its label produced a silent misconfiguration rather than a loud failure. A single wide-channel label is now expanded to the correct member list above 20 MHz bonding, an explicit member list passes through, and a label that lines up with no valid member set is rejected.
- **The policy safety gate normalizes inside itself, and what it is fed is pinned (#73, works #69).** Normalization living outside the gate meant a caller reaching the gate by another route got an unnormalized action.
- **Nine of the ten backlog findings from the #65 review (#74, works #71).** Global-ADOM object paths, unvalidated `task_id` on `delete_task`, a quote-span scan that closed on an escaped quote, a bulk device string iterated one character at a time, a protocol allowlist too narrow for the lookup it served, and an unredacted preview result. The tenth, a hand-rolled error envelope, was refused on measurement: converting the one site named would have made it inconsistent with 260 neighbours rather than consistent with 10, which is a contract change belonging in its own issue.
- **A partial update is gated against the policy it will produce, not the fields it carries (#75, works #71).** `update_local_in_policy` left the gate ungated when `action` was omitted, so an update that omitted the field could widen a policy without being screened. The gate now reads through to the resulting policy, and an unreadable action is a sentinel that fails closed rather than a value that reads as permissive.
- **A request size is no longer reported as an outcome count (#81, closes #78).** Bulk group tools returned the number of members **asked for** as though it were the number acted on, so a partial or total failure still reported full success. The counts now come from the appliance response.
- **Five more review-backlog issues, three of them wider than filed (#87, closes #82, #83, #84, #85, #86).** Security-profile CRUD (AV, web filter, DNS filter, app control, IPS, SSL/SSH, DLP, WAF) addressed the Global ADOM as `adom/global` where FMG expects `global`, and the bug lived in four shared constants, not the list tools the issue named, so create/get/update/delete were affected on all eight profile types too (#82). `capture_id` reached the wire with no validation: a bool, a negative, or a float all passed (#83). `policy_lookup` accepted ICMPv6 together with an IPv4-only address, an unanswerable combination now refused rather than silently answering the wrong half of it (#84). A PEM certificate split across list elements in a redacted preview leaked every line after the first (#85). `dvm_tools.add_devices_bulk` had no shape check on `devices`, so a single dict or a bare string reached the payload builder and failed with an opaque internal error instead of a clear one (#86).
- **A stock appliance's certificate cannot pass the verification the old warning recommended enabling (#90, closes #89).** The certificate is self-signed with no SAN, so trusting it and turning verification on fails with an IP-address mismatch regardless — the warning was pointing operators at a step that cannot succeed. It now names the real prerequisite (a certificate whose SAN matches the connection address), and a new `FORTIMANAGER_CA_BUNDLE` setting lets an estate that has done that work verify against a specific CA instead of choosing between "off" and "everything fails."
- **Two leftovers from the mcp 2.0 port are cleaned up (#96, closes #95, by Christian Dassy / [@inxbit](https://github.com/inxbit)).** mcp 2.x uses `httpx2`, which logs under its own name, so the noise suppression in `configure_logging` was silencing an `httpx` logger this tree no longer has, and `httpx` itself was still a declared dependency that nothing imported. Starlette pulls it only under a `full` extra this project does not install. The suppression now names `httpx2` and the dependency is gone. The `pydantic-settings` and `starlette` security floors added by the port are unchanged. Two contract tests pin both halves, so re-adding `httpx` or reverting the logger name fails rather than passing quietly.

### Changed

- **The server is ported to the mcp 2.0 `MCPServer` API and the `<2` pin is lifted (#92).** mcp 2.0 removed `mcp.server.fastmcp`, the API this server was built on, so the old `mcp>=1.28.1,<2` pin was holding CI green rather than describing a supported range. The floor is now `mcp>=2.0.0`, and it is a hard import requirement rather than a preference: the 2.0.0 wheel ships `mcp/server/mcpserver` and drops `fastmcp`, the 1.28.1 wheel is the exact reverse, so an install below the floor cannot start at all rather than degrading quietly. **Upgrading an existing deployment therefore needs its dependencies reinstalled, not only its source synced.** The migration is largely a rename, with one part that fails silently: `MCPServer` accepts neither `stateless_http` nor `transport_security`, both having moved to `streamable_http_app()`, so dropping them from the constructor without adding them to the transport would have left the HTTP deployment stateful and unbound by `MCP_ALLOWED_HOSTS` with nothing reporting it. Both are now passed at the transport and pinned by tests that record the call `run_http` makes, because `MCPServer.settings` has no `stateless_http` field to assert against. Masking is unaffected: it runs before the `CallToolResult` conversion 2.x introduced, so the new return shape never reaches redaction.

Sending `passphrase` for SAE is rejected by the appliance with "vap sae password must be not empty". ### Added

- **Reversible data masking (FPE), opt-in and off by default** ([#34](https://github.com/rstierli/fortimanager-mcp/issues/34)). `MASKING_ENABLED=true` plus a 32/48/64 hex-character `FMG_MASKING_KEY` masks the identifier-bearing *values* in tool outputs (addresses, subnets, MACs, device serials, FQDNs, admin usernames) with format-preserving encryption, so a model can still correlate a value across calls without seeing it. Enabling the flag without a valid key aborts startup rather than running unmasked. The ciphers are shared with the FortiAnalyzer sibling under `faz-mcp-fpe:v1`, so one key produces matching tokens on both, which also means one blast radius: rotate them together.

  **Names are never masked.** Object, ADOM, package, VDOM, device, template and script names are routing keys; masking one would not hide an identifier, it would break every follow-up call that used it.

  **Masked values are read-only context.** A token supplied as a tool argument is refused rather than restored. FortiManager arguments become estate configuration, and the v1 token format carries no integrity tag, so a stale, rotated or foreign token would decrypt to a plausible wrong address and be written with nothing to catch it. An authenticated envelope that would make restoration safe is the subject of the joint protocol v2 RFC.

  **Fail-closed by construction.** A value the ciphers cannot represent becomes an irreversible keyed placeholder, never the raw value, and is never logged. A carrier key holding a container is walked rather than returned. If masking a whole result fails, the tool returns an error envelope and the raw result is withheld. Secrets are replaced by a fixed constant instead of a token, since a token is reversible by design, and that constant is itself refused on the way back in.

  Deliberately out of scope for this version, each with a reason rather than an oversight: free text, script bodies, install previews and task detail, and names that embed an address.

  Carrier coverage was set by static derivation over every tool module plus read-only sweeps of live FortiManager 7.6.7 and 8.0.0, then corrected three times by review against a live FortiGate device DB: the SD-WAN source and gateway fields, the interface IPv4 and IPv6 address, relay and VRRP fields, MAC-type address objects, wildcard FQDNs, service IP ranges, the proxy envelope's device serial, and the interface address fields that carry a netmask alongside the address. `adm_pass` and its siblings are redacted rather than tokenised.

## [1.6.0] - 2026-06-12

Async-task contract (bundle C of [#11](https://github.com/rstierli/fortimanager-mcp/issues/11)): anti-exhaustion guards for the FMG task lifecycle — bounded concurrent task spawns, deadline-bounded status polls, and a shared poll-recovery budget. Adapted from the FortiAnalyzer MCP's logsearch guards ([fortianalyzer-mcp#18](https://github.com/rstierli/fortianalyzer-mcp/pull/18)). 400 unit tests pass.

### Added
- **Shared in-flight task budget** (`utils/task_guard.py`). The seven task-spawning tools (`install_package`, `install_device_settings`, `preview_install`, `execute_script_on_device/devices/device_group/package`) now share one in-process budget of `TASK_CONCURRENCY_LIMIT = 5` concurrent FMG tasks, so a caller cannot slam the FMG with 20 parallel installs. The slot is reserved *before* the submit is awaited (racing spawns cannot overshoot), bound to the returned task id, and released when `wait_for_task` observes a terminal state — or reclaimed after `TASK_SLOT_TTL` (30 min) for callers that never poll. When the budget is full the tool fails fast with a structured `task_slots_exhausted` envelope naming the in-flight kinds, rather than queueing the MCP request.
- **Deadline-bounded task polling in `wait_for_task`.** Each `get_task` poll is bounded by `asyncio.wait_for` (`POLL_CALL_TIMEOUT = 30s`), the overall wait is clamped to `MAX_TASK_WAIT_TIMEOUT = 3600s`, and `poll_interval` is clamped to `[1, 60]` so a 0 interval cannot hot-loop. Wedged polls re-poll on a shared budget of `MAX_TASK_POLL_FAILURES = 3` (the FMG analog of FAZ's `MAX_SEARCH_REISSUES`), then surface a structured `task_poll_failed` envelope. Persistent API errors still surface immediately — `get_task` already retries transients internally, so re-polling those here would be wrong.

### Notes (FMG adaptations of the FAZ pattern)
- **No automatic cleanup-cancel of FMG tasks.** FAZ cancels an orphaned logsearch (read-only, single-use tid). An FMG task is a config-mutating install or script run: auto-cancelling one mid-flight because the *poll* was aborted risks a half-applied install, which is worse than letting the task finish unobserved. Exhaustion protection comes from the slot TTL instead.
- The `assign_*` bulk operations named in #11 turn out to be synchronous (no task id in their responses), so they need no guard. The guard is one `spawn_guarded(...)` wrapper per call site if other spawn sites (e.g. dvm `create_task`-flag tools, `validate_template`) should be added later.

- **The HTTP transport now fails closed when `MCP_AUTH_TOKEN` is unset.** The streamable-HTTP server fronts the full tool surface (including device add/delete, policy install, and script execution on managed devices), so it previously could serve everything unauthenticated if the token was simply forgotten. `run_http()` now refuses to start without a token and exits with a message that names the fix, unless the operator explicitly opts out with `MCP_ALLOW_NO_AUTH=true` (logged at CRITICAL; intended only for a trusted, isolated bind such as 127.0.0.1 behind a gateway). **Upgrade note:** a deployment that ran on a `0.0.0.0` bind without a token must now set either `MCP_AUTH_TOKEN` or `MCP_ALLOW_NO_AUTH=true` to keep starting.

## [1.4.1] - 2026-06-12

Three bugs found and fixed by live verification against a lab FortiManager 7.6.7 (v7.6.7-build3737). 388 unit tests pass.

### Fixed
- **Script target enum was swapped on the FMG 7.6+ endpoint** — every `execute_script_on_package` call failed with `-8 Invalid parameter`. `_SCRIPT_TARGET_MAP` had `adom_database=1 / remote_device=2`; verified by execution (a create+get round-trip cannot detect a swap because the mapping is symmetric): a `target=2` script executes against a policy package and spawns a task, a `target=1` script accepts a device-scoped execute. Correct map: `device_database=0, remote_device=1, adom_database=2`. Scripts created through the MCP with `target="adom_database"` were actually stored as remote-device scripts and vice versa.
- **`add_model_device` omitted the `mr` field** — every model-device add failed with `Unsupported device/ADOM version`. FMG expects the major version in `os_ver` (`"7.0"`) and the minor in a separate `mr` integer. The tool now splits `os_version` "X.Y" into `os_ver="X.0"` + `mr=Y` (verified live: device lands as FortiOS 7.6).
- **FMG error-code table corrected to live-verified semantics.** The previous table mislabeled most codes: `-2` is "Object already exists" (was: invalid session — a duplicate create triggered a spurious re-login + retry), `-3` is "Object does not exist" (was: permission denied), `-8` is "Invalid parameter" (was: ADOM locked), `-10` is "data invalid for selected URL" (was: version mismatch), and `-11` is "no permission / **stale session**" (was: task timeout, retried twice with the same dead session). Newly mapped: `-22` login fail, `-10147` no write permission, `-20055` workspace locked by another admin. Consequences: `_RECONNECTABLE_ERROR_CODES` is now `{-11}` — the reconnect-once path (#14/#16) now actually triggers on the code the FMG emits for a stale session — and `_TRANSIENT_ERROR_CODES` is `{-1}`.

## [1.4.0] - 2026-06-10

Hardening pass: ports the FortiAnalyzer MCP's resilience and observability patterns (PRs [fortianalyzer-mcp#17](https://github.com/rstierli/fortianalyzer-mcp/pull/17), [#18](https://github.com/rstierli/fortianalyzer-mcp/pull/18), [#22](https://github.com/rstierli/fortianalyzer-mcp/issues/22) by Christian Dassy / [@inxbit](https://github.com/inxbit)) over to FortiManager. Tracked in #11. 424 unit tests pass.

### Added
- **Shared error envelope + secret redactor** ([#12](https://github.com/rstierli/fortimanager-mcp/pull/12)). New `utils/responses.py` provides `error_response(error, message, operation, ...)` — one structured envelope used by every tool error path with stable machine code, redacted + length-bounded human text, optional `adom`/`package`/`device`/`task_id` fields included only when supplied. `redact()` scrubs `key=value` / `key: value` pairs whose key matches `SENSITIVE_FIELDS` (excluding the generic words `key`/`auth`/`pass` to avoid mangling policy names) and masks long hex token-like runs. Tool wiring to use the envelope ships in a follow-up.
- **`FORTIMANAGER_VERIFY_SSL=false` connect-time warning** ([#13](https://github.com/rstierli/fortimanager-mcp/pull/13)). When SSL verification is disabled, a single `logger.warning` at connect time names the host, mentions the env var by name, and nudges toward importing the FortiManager CA into the system trust store. Default remains `True` (v1.3.0 stability); anyone hitting this warning has explicitly opted into insecure.
- **`async ensure_connected()` + serialized reconnect-once foundation** ([#14](https://github.com/rstierli/fortimanager-mcp/pull/14)). Tools call `await client.ensure_connected()` before requests so idle-closed sessions are transparently revived instead of surfacing raw "Not connected" errors. `_force_reconnect()` is serialized via `asyncio.Lock` + generation counter so concurrent dropped-session callers only re-log in **once**; the rest observe the bumped generation and bail out.
- **Bounded transient-retry wrapper wired through every API method** ([#16](https://github.com/rstierli/fortimanager-mcp/pull/16)). New `_execute_resilient()` runs each request with reconnect-once on session error (auth, codes `-2`/`-20`/`-21`, raw "Not connected" when previously connected) and bounded transient retry on `OSError` or codes `-1`/`-11` with exponential backoff (`0.5s`, `1.0s`). Annotates raised exceptions with `.retries_attempted` so `error_response()` surfaces `retry_count`. Every typed wrapper (101 tools) picks up the resilience without per-method changes.

### Changed
- **Server lifecycle ownership consolidated** ([#15](https://github.com/rstierli/fortimanager-mcp/pull/15)). Dropped the top-level `lifespan()` and the `lifespan=lifespan` kwarg on `mcp = FastMCP(...)`. With `FastMCP`'s `stateless_http=True` shape that lifespan was running per request/session, connect-then-disconnect cycling the global `_fmg_client` around every call and dropping the session under concurrent requests. Lifecycle ownership now lives in exactly two paths: `run_http()` → `app_lifespan` (HTTP mode, already existed and was already correct) and a new `run_stdio()` → `stdio_main` (stdio mode). HTTP user-visible behavior is unchanged; the per-request lifespan that was running redundantly alongside `app_lifespan` is now gone.
- **Transient FMG errors are silently retried before surfacing.** Callers see slightly longer wait on a transient failure (up to ~1.5s of backoff) in exchange for the failure not happening at all most of the time. Validation, permission, not-found, and ADOM-locked errors remain surfaced immediately — these aren't transient and retrying them would be wrong.

## [1.3.0] - 2026-05-29

First stable release — graduated from beta.

### Security
- **Input validation enforced at tool boundaries** ([#10](https://github.com/rstierli/fortimanager-mcp/issues/10)): identifier parameters (`adom`, `device`, object/policy/package/template/script names) are now validated before being interpolated into API request paths, closing a path-injection vector. Object and policy name patterns permit parentheses and colons (e.g. cloned `addr (1)`, `grp:prod`); path separators, shell metacharacters, and quotes are rejected.
- **Stored scripts re-validated in the execute path** ([#10](https://github.com/rstierli/fortimanager-mcp/issues/10)): `execute_script_on_device/devices/group/package` now re-check the resolved script body against the safety denylist (previously only `create_script`/`update_script` were checked, so a script created with safety disabled or pre-existing on the FMG could execute unguarded). The denylist is broadened beyond destructive exec commands to cover backdoor-admin creation (`config system admin`), permissive firewall actions (`set action accept`), disabling logging (`set status disable`), and DNS/route changes — with whitespace normalization to prevent spacing/case bypass.
- **API error bodies sanitized** ([#10](https://github.com/rstierli/fortimanager-mcp/issues/10)): tool errors now return a generic message plus an error code instead of the raw FortiManager error text, preventing internal endpoint paths from leaking to the caller. Full detail is still logged server-side.
- **Pinned `pyfmg` dependency** ([#10](https://github.com/rstierli/fortimanager-mcp/issues/10)) to a specific commit instead of a floating fork reference.

### Changed
- **Stability promotion:** no functional changes beyond the security hardening above. TLS guidance now recommends importing the FortiManager CA certificate; `FORTIMANAGER_VERIFY_SSL=false` is documented only as a warned last resort, and shipped example configs default to verification enabled.
